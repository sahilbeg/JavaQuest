# Messaging: the transactional outbox

Billing never heard about some ended rides, and once it billed a ride whose rental update had rolled back. Both bugs come from writing to the database and publishing to the broker as two separate steps. Fix it with the three parts of the outbox pattern:

1. **`RideEndService`** writes the rental change and the event into the Rentals database, in **one** transaction.
2. **`OutboxRelay`** copies unsent events from the outbox table to the broker, in order, and marks each one sent.
3. **`BillingConsumer`** handles each event **once**, even when the broker delivers it twice.

Use `PreparedStatement` with `?` parameters, and close every statement and result set with try-with-resources.

## Given, already finished

- `BikeType`: `CLASSIC`, `EBIKE`, `CARGO`. `type.fareCents(minutes)` is 100 cents to unlock plus the minutes at 15, 30 or 25 cents.
- `RideEnded`: the event record `(eventId, rentalId, riderId, bikeId, type, minutes, fareCents)`. `toJson()` turns it into one line of JSON, and `RideEnded.fromJson(text)` reads it back.
- `Message`: what the broker carries, `(eventId, topic, key, payload)`.
- `MessagePublisher`: one method, `void publish(Message message)`. It **throws a `RuntimeException`** when the broker did not confirm the message.

## The tables

The checks create every table before they call your code. Your code never creates or drops tables. Each check gets a fresh in-memory H2 database.

The Rentals database:

```sql
CREATE TABLE rental (
    id         VARCHAR(20) PRIMARY KEY,
    rider_id   VARCHAR(20) NOT NULL,
    bike_id    VARCHAR(10) NOT NULL,
    bike_type  VARCHAR(10) NOT NULL,   -- 'CLASSIC', 'EBIKE' or 'CARGO'
    status     VARCHAR(10) NOT NULL,   -- 'ACTIVE' or 'ENDED'
    minutes    INT,                    -- NULL while the ride is ACTIVE
    fare_cents BIGINT                  -- NULL while the ride is ACTIVE
);
CREATE TABLE outbox (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,   -- 1, 2, 3... in the order rows are written
    event_id    VARCHAR(40) NOT NULL UNIQUE,
    topic       VARCHAR(40) NOT NULL,
    message_key VARCHAR(40) NOT NULL,
    payload     VARCHAR(1000) NOT NULL,
    sent        BOOLEAN DEFAULT FALSE NOT NULL
);
```

The Billing database, a separate database owned by the Billing service:

```sql
CREATE TABLE processed_event (
    event_id VARCHAR(40) PRIMARY KEY
);
CREATE TABLE rider_bill (
    rider_id    VARCHAR(20) PRIMARY KEY,
    total_cents BIGINT NOT NULL,
    rides       INT NOT NULL
);
```

## How the checks work

Each check opens fresh in-memory H2 databases with the tables above. Your code gets one connection. The checks look through a second connection, so they only see what you **committed**.

A fake broker stands in for the real one. It can fail on a chosen message, or keep a message and still throw, as if its "got it" answer was lost. One check makes the outbox insert fail by reusing an event id. Another hides the `rider_bill` table to make the bill update fail.
